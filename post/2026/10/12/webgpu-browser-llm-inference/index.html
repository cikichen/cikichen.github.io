浏览器也能跑 LLM?是的,而且不慢

2025 年 11 月,Chrome、Edge、Safari 相继默认启用 WebGPU——浏览器原生跑大模型从实验阶段正式进入可部署阶段。截至 2026 年 10 月,WebGPU 全球浏览器覆盖率约 85%(caniuse 口径,截至 2026-10-12 验证),Firefox 的 Windows 版已在 141 版本支持,Linux 还在 Nightly。

这意味着:模型权重缓存在用户浏览器里,推理走用户自己的 GPU,没有服务器、没有 API 费用、不上传 prompt。对隐私敏感工具、离线应用、免后端 Demo 来说,这是端侧 AI 里最被低估的一条部署路径。

原理:三件套

浏览器 LLM 推理由三个组件协作:

  1. WASM 推理内核(如 WebLLM 用 Apache TVM 编译的 WebGPU 着色器代码 WGSL,实现了 PagedAttention 和 FlashAttention)
  2. 量化模型权重(4-bit 量化后,1.5B 模型约 1GB,只需下载一次,之后走浏览器 Cache API 或 OPFS)
  3. Web Worker(推理搬离主线程,UI 不卡顿)

框架怎么选:三个主流方案对比

方案 引擎 定位 维护状态(截至 2026-10-12)
WebLLM MLC-LLM + TVM,WebGPU 聊天类 LLM 推理,OpenAI 兼容 API 活跃,v0.2.85,GitHub 17.9k star
Transformers.js ONNX Runtime Web,WebGPU 全任务(嵌入/图像/语音/LLM),200+ 架构 活跃,v4.3.0,v4 起 C++ 重写 WebGPU 运行时
wllama llama.cpp 编译为 WASM 直接复用 GGUF 模型,CPU 可跑 + WebGPU 活跃,含 WebGPU 后端

选型口诀:要聊天对话 → WebLLM(API 跟 OpenAI 几乎一一对应);要嵌入、分类、OCR、ASR 等多任务 → Transformers.js(v4 在高端硬件上跑 GPT-OSS 20B q4 可达约 60 tok/s);已有 GGUF 生态、想 CPU/GPU 通吃 → wllama。

import { CreateMLCEngine } from "@mlc-ai/web-llm";

// 模型来自 HuggingFace 的 MLC 格式:Qwen2.5-1.5B,4-bit 量化,约 1GB
const engine = await CreateMLCEngine(
  "mlc-ai/Qwen2.5-1.5B-Instruct-q4f16_1-MLC",
  { initProgressCallback: (p) => console.log(`${p.progress}%`) }
);

const reply = await engine.chat.completions.create({
  messages: [{ role: "user", content: "用一句话介绍 WebGPU" }],
  stream: true, // 流式输出
});

注意三点:先 navigator.gpu 检测再创建引擎;模型第一次下载走浏览器缓存,二次加载是本地读取;官方文档明确 Function Calling 仍是进行中,别依赖。

import { pipeline } from "@huggingface/transformers";
import { env } from "@huggingface/transformers";

env.useWasmCache = true; // 缓存 WASM 运行时,首次加载后可完全离线

// 图片分类走 WebGPU
const classifier = await pipeline(
  "image-classification",
  "onnx-community/mobilenetv4_conv_small.e2400_r224_in1k",
  { device: "webgpu" }
);

// Whisper 语音识别同样一句话切换
const transcriber = await pipeline(
  "automatic-speech-recognition",
  "onnx-community/whisper-tiny.en",
  { device: "webgpu" }
);

性能参考(截至 2026-10-12 验证,官方/实测数据)

  • WebLLM 在 Apple M3 Max 上跑 Llama 3.1 8B 4-bit:约 41 tok/s,约为原生 MLC-LLM 的 80%;Phi 3.5 Mini 约 71 tok/s
  • WebGPU 首次运行要编译 WGSL 着色器,有 3-10 秒冷启动窗口,Chrome/Edge 实现最完整
  • GPU 厂商驱动 bug 仍存在(NVIDIA 572.xx 系列在 RTX 30/40 上偶发崩溃),生产环境要捕获 Device Loss 并回退

生产建议:别 All-in 本地,做混合路由

2026 年业界主流做法不是纯浏览器推理,而是路由层:轻量门控模型(如 TinyLlama 级别,延迟低于 20ms)判断查询复杂度——短问答、单句改写、分类等延迟敏感任务走本地(毫秒级响应);复杂多步推理、长文分析走云端 API。可以再加置信度路由:本地模型输出置信度低时自动切云端重试,WebLLM 的 API 暴露了 token 对数概率,可用来做这个判断。

边界要清楚:本地推理只缩小一条数据路径,不等于隐私合规;用户设备没 WebGPU、内存不足、模型超 2GB 时,该回退就回退,回退前要征得用户同意。

总结

浏览器是端侧 LLM 最容易分发的地方——用户打开链接即用,零安装。选 WebLLM 做对话,选 Transformers.js 做全任务,用 wllama 复用 GGUF 模型;把推理接口与推理位置解耦,先本地后云端路由。这套组合在 2026 年已经足够支撑真实产品,而不再是 Demo。
